### 2.2 运行步骤

```bash
# 1. 克隆项目
git clone https://github.com/lxy123-aka/app-review-analyzer.git
cd app-review-analyzer

# 2. 安装依赖
pip install -r requirements.txt

# 3. 配置环境变量（可选，不配置则使用离线缓存）
cp .env.example .env
# 编辑 .env，填入 LLM_API_KEY 等

# 4. 启动应用
streamlit run app.py
```

浏览器自动打开 `http://localhost:8501`。

## 三、复盘总结

### 3.1 项目亮点

1. **全链路可追溯设计**：从评论→主题→发现→需求→测试用例，每一层都带 source_review_ids，validator 纯规则校验通过率 100%，真正实现了"每个结论都有证据"。

2. **防幻觉三重防护**：Prompt 约束 + 生成时代码过滤无效 ID + validator 再校验，有效防止 LLM 编造 review_id，保证了分析结果的可信度。

3. **动态主题发现**：不使用固定关键词映射或预定义分类，由 LLM 从任意 App 的评论中动态归纳问题主题，泛化能力强，换不同 App 输出不同结果。

4. **离线缓存降级方案**：预生成笔试指定 App 的完整管线输出缓存，无 API Key 时自动加载并醒目标记，解决了面试官离线审查的痛点。

5. **模块化架构清晰**：抓取/清洗/分析/PRD/测试用例/验证各模块独立单一职责，orchestrator 统一编排，错误隔离不崩溃，易于维护和扩展。

### 3.2 遇到的主要挑战与解决

| 挑战 | 解决方案 |
|:---|:---|
| LLM 输出非严格 JSON 导致解析失败 | 实现 safe_json_loads() 容错解析，正则提取 JSON 内容 |
| 无 API Key 时应用崩溃无法演示 | 预生成离线缓存 + 自动检测加载 + 醒目标记 |
| 大批量评论分析耗时久 | 批量处理（30条/批）+ 低温度 + 进度实时展示 |
| Streamlit 交互重复执行流水线 | session_state 持久化结果 + 按钮触发才重新执行 |
| 超长评论触发 API 长度限制 | 评论内容截断至 1500 字符 + 省略号 |
| 核心文件漏提交到 GitHub | git add -A 全面检查 + 全新 clone 回归验证 |

### 3.3 当前局限

1. **数据量限制**：Apple RSS Feed 最多约 500 条评论，无法覆盖全部历史评论，长尾问题可能遗漏。已在 UI 中透明说明。

2. **语言覆盖**：主要针对英文评论优化，多语言混合场景下 LLM 分析质量可能下降。已支持语言检测标记，但未做翻译处理。

3. **LLM 成本**：全流程分析约需 10+ 次 LLM 调用，500 条评论时 API 成本约 0.5-1 元（DeepSeek），可接受但非最优。未来可引入缓存复用机制。

4. **语义校验为可选**：当前 validator 主要是 ID 存在性的规则校验，语义一致性校验（LLM 判断需求是否真的从评论推导）为可选功能，LLM 不可用时跳过。

5. **无 A/B 验证**：生成的 PRD 和测试用例是基于评论证据的分析建议，未与实际产品迭代效果做 A/B 对比验证。

### 3.4 未来优化方向

1. **多数据源整合**：除 Apple RSS 外，支持 Google Play 评论、社交媒体反馈等多源数据合并分析，扩大数据覆盖面。

2. **RAG 架构优化成本**：将历史评论向量化存入本地向量数据库，新增评论先做相似度检索复用已有分析结果，预计可降低 60%+ 的 LLM 调用成本。

3. **时间序列趋势分析**：增加评论随时间变化的趋势分析，识别问题是恶化还是改善，为版本迭代效果提供数据支撑。

4. **导出与集成**：支持将 PRD 和测试用例导出为 Jira/飞书/禅道等项目管理工具格式，直接接入团队工作流。

5. **多模型对比**：支持同时调用多个 LLM 模型（DeepSeek/GPT-4/Claude）对同一批评论做分析，对比结果差异，提升分析鲁棒性。

6. **用户反馈闭环**：收集用户对 AI 分析结果的反馈（有用/无用/需修改），用于优化 Prompt 和分析策略，形成持续改进闭环。

### 3.5 个人收获

1. **vibe coding 实践**：全程使用 AI 编程助手辅助开发，从需求拆解到代码实现到调试修复，体会了"人机协作"的高效开发模式。AI 在代码生成、文档编写、错误排查方面大幅提升了效率，但核心架构设计和质量把控仍需人工主导。

2. **可追溯性设计的重要性**：在 LLM 生成内容占比高的项目中，"每个结论都有证据"不是可选的，而是必须的。通过 source_review_ids + validator 的设计，有效解决了 LLM 幻觉和无依据结论的问题。

3. **离线降级的产品思维**：技术项目交付不能假设用户一定有 API Key 和网络环境。离线缓存 + 自动降级 + 醒目标记的方案，让项目在任何环境下都能展示效果，这是产品思维在技术项目中的体现。

4. **确定性与模型驱动的边界**：不是所有环节都要用 LLM。清洗、去重、验证等确定性操作用规则更高效、更可靠；主题发现、需求生成、测试用例生成等语义任务用 LLM 更灵活。合理划分边界是项目成功的关键。
