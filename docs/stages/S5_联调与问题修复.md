## 二、问题清单与修复说明

### 问题 1：无 API Key 时应用崩溃，无法离线演示

**问题分类**：功能缺陷 / 体验问题

**发现时间**：联调阶段第 2 轮

**问题描述**：
当 `.env` 中未配置 `LLM_API_KEY` 时，`LLMClient.__init__()` 在初始化时直接抛出 `LLMCallError`，导致 Streamlit 应用页面报错崩溃，用户无法看到任何内容。面试官在无网络/无 API Key 环境下无法审查项目效果。

**影响范围**：
- 离线演示完全不可用
- 新用户首次运行（未配置 API Key）直接报错
- 不符合笔试要求"any necessary sample output or cached data so that interviewers can review the results even when external network access is unavailable"

**根因分析**：
- `LLMClient` 设计为初始化时即校验 API Key，缺失直接抛异常
- UI 层没有对 LLM 不可用的情况做降级处理
- 没有预生成的离线缓存数据

**修复方案**：
1. 预生成笔试指定 App（839285684）的完整管线输出缓存，保存为 `data/cached_result_app_839285684.json`
2. 在 `app.py` 中增加 `load_cached_result()` 函数，读取缓存 JSON，文件不存在或解析失败时返回 None，不崩溃
3. 增加 `_build_pipeline_result_from_cache()` 函数，将缓存 JSON 构造为 `PipelineResult` 对象，填充 8 个步骤和所有分区数据
4. 页面初始化时自动检测：`settings.validate_llm()` 缺失配置 + 尚无结果 + 用户未点击按钮 → 自动加载缓存
5. 缓存模式下在结果区顶部显示 `st.warning` 醒目标记："⚠️ 当前显示缓存示例数据（App ID: 839285684），非实时分析结果"
6. 同时提供手动"加载离线缓存结果"按钮作为兜底

**修复后验证**：
- 删除 `.env` 中的 API Key，重启应用 → 自动加载缓存，页面正常显示完整分析结果，顶部有缓存标记 ✅
- 恢复 API Key → 实时分析流程不受影响，缓存不干扰实时结果 ✅
- 缓存文件损坏 → `load_cached_result()` 返回 None，不崩溃，UI 提示配置 API Key ✅

**联调结果**：通过

### 问题 3：LLM 偶尔输出非严格 JSON，导致解析失败

**问题分类**：稳定性问题

**发现时间**：联调阶段第 3 轮（大批量评论测试时）

**问题描述**：
当评论数量较多（>200条）或评论内容复杂时，LLM 偶尔会在 JSON 输出前后附加解释性文字（如"以下是分析结果："），导致 `json.loads()` 解析失败，整个分析流程中断。

**影响范围**：
- 大批量评论分析时偶发失败
- 用户需要重新运行，体验不佳

**根因分析**：
- 虽然 System Prompt 要求"必须返回严格的 JSON，不要附加任何解释性文字"，但 LLM 仍有小概率不遵守
- 原代码直接使用 `json.loads()`，无容错处理

**修复方案**：
1. 实现 `safe_json_loads()` 容错解析函数（位于 `utils/helpers.py`）：
   - 先尝试直接 `json.loads()`
   - 失败则用正则提取第一个 `{` 到最后一个 `}` 之间的内容再解析
   - 仍失败则返回空 dict，记录日志
2. `LLMClient.chat_json()` 调用 `safe_json_loads()` 而非直接 `json.loads()`
3. 解析失败时记录日志但不崩溃，Analyzer 对空结果做容错处理（跳过该批次）

**修复后验证**：
- 构造 LLM 输出含前置文字的测试用例 → `safe_json_loads()` 成功提取 JSON ✅
- 250条评论连续运行 5 次 → 无解析失败，流程稳定 ✅
- 完全无效的输出 → 返回空 dict，不崩溃，记录日志 ✅

**联调结果**：通过

### 问题 4：Streamlit 交互导致重复执行流水线

**问题分类**：性能问题

**发现时间**：UI 联调阶段

**问题描述**：
用户在结果页切换 Tab 或调整侧边栏筛选条件时，Streamlit 会重新执行整个脚本，导致 `run_pipeline_from_url()` 被重复调用，重新抓取评论和调用 LLM，既浪费时间又消耗 API token。

**影响范围**：
- 每次交互都重新执行完整流水线，等待时间长
- API token 不必要消耗
- 用户体验差

**根因分析**：
- Streamlit 的交互模型是"每次交互重新执行整个脚本"
- 流水线结果未持久化到 `st.session_state`
- 没有判断"是否已经执行过"的逻辑

**修复方案**：
1. 流水线执行完成后，将 `PipelineResult` 存入 `st.session_state["pipeline_result"]`
2. 页面渲染时优先从 `st.session_state` 读取结果，只有用户点击"开始分析"按钮时才重新执行
3. 使用 `st.status` 上下文管理器展示执行进度，避免进度状态丢失
4. 新增 `is_cached` 状态标记，区分实时结果和缓存结果

**修复后验证**：
- 执行一次流水线后切换 Tab → 不重新执行，结果秒开 ✅
- 点击"开始分析" → 正常重新执行 ✅
- 刷新页面 → session_state 重置，符合预期 ✅

**联调结果**：通过

### 问题 5：超长评论触发 LLM API 最大输入长度限制

**问题分类**：边界异常

**发现时间**：边界场景测试阶段

**问题描述**：
当单条评论内容超过 2000 字符时，批量传入 LLM 后总 token 数超过 API 限制，导致请求失败。Apple RSS 中偶有超长评论（用户写长篇反馈）。

**影响范围**：
- 包含超长评论的批次分析失败
- 极端情况下整个分析流程中断

**根因分析**：
- 评论内容未做长度截断
- 批量 30 条时如果多条超长，总 token 容易超限

**修复方案**：
1. 在 `build_user_prompt()` 构造评论数据时，对每条评论内容截断至 1500 字符，超出部分加省略号
2. 截断不影响 review_id 等元数据
3. `_BATCH_SIZE` 保持 30，截断后单批 token 数安全在限制内

**修复后验证**：
- 构造 5000 字符超长评论 → 截断为 1500 字符 + 省略号，API 请求成功 ✅
- 250条评论（含3条超长）完整分析 → 无失败，全部成功 ✅
- 正常长度评论不受影响 ✅

**联调结果**：通过

### 问题 6：Apple RSS 分页边界处理不当

**问题分类**：边界异常

**发现时间**：数据抓取联调阶段

**问题描述**：
当 App 评论数不足 500 条（不足 10 页）时，循环到空页后仍继续请求，导致不必要的网络请求和错误日志。部分 App 的 RSS 在最后一页之后返回相同数据而非空数据，可能导致重复抓取。

**影响范围**：
- 评论少的 App 会产生无效请求
- 极端情况可能重复抓取相同评论

**根因分析**：
- 原代码固定循环 max_pages 次，未检测空页提前终止
- 未对重复数据做检测

**修复方案**：
1. 每页请求后检查 `entries` 是否为空，为空则 `break` 提前终止循环
2. 去重逻辑在 Cleaner 阶段兜底（按 review_id 去重），即使抓取重复也会被清洗
3. 抓取报告中记录 `pages_attempted`、`pages_succeeded`、`pages_failed`，透明展示抓取情况

**修复后验证**：
- 评论数少的 App（约 100 条）→ 抓取 3 页后检测到空页提前终止，无无效请求 ✅
- 评论数多的 App → 抓取满 10 页/500 条，正常终止 ✅
- 重复评论 → Cleaner 阶段按 review_id 去重，无重复 ✅

**联调结果**：通过
