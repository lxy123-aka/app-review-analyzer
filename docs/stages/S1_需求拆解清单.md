# S1 需求拆解清单

> 项目：App Store 评论分析与版本规划工具
> 阶段：需求拆解
> 日期：2026-08-20

---

## 一、项目目标与业务价值

### 1.1 项目背景

产品团队在迭代 App 时，需要从海量用户评论中挖掘真实痛点、规划版本需求、设计测试用例。传统方式依赖人工逐条阅读评论，效率低、易遗漏、难以量化。本项目旨在构建一个**基于大模型的 App Store 评论全流程分析工具**，将"评论→问题→需求→测试用例"的链路自动化、可追溯化。

### 1.2 核心目标

- **数据真实可复现**：通过 Apple 官方 RSS Feed 抓取美国区真实评论数据，不依赖页面爬取
- **动态语义分析**：由 LLM 从评论中自动发现问题主题，不使用固定关键词映射或预定义分类
- **全链路可追溯**：每条需求、每个测试用例都能回溯到具体的用户评论 ID
- **证据驱动**：每个发现都附带源评论、样本数、置信度和冲突证据，杜绝无依据结论
- **可本地运行**：Streamlit Web UI，单条命令启动，支持离线缓存演示

### 1.3 业务价值

| 价值维度 | 描述 |
|:---|:---|
| **效率提升** | 将人工阅读数百条评论并归纳问题的时间从数小时缩短至分钟级 |
| **决策质量** | 基于真实评论证据生成 PRD，减少主观臆断和"拍脑袋"需求 |
| **测试覆盖** | 自动生成与需求、评论关联的测试用例，确保用户痛点被验证 |
| **团队协作** | 结构化输出便于产品、研发、测试团队对齐需求来源和优先级 |

## 二、核心功能需求矩阵

| 功能模块 | 核心输入/触发条件 | 预期输出 | 验收标准（量化/质化） |
|:---|:---|:---|:---|
| **App Store 评论抓取** | 用户输入美国区 App Store 链接（如 `https://apps.apple.com/us/app/xxx/id839285684`） | 结构化评论列表（review_id、内容、评分、版本、作者、日期） | 使用 Apple 官方 RSS Feed，非页面爬取；支持分页（最多10页/500条）；请求间隔≥1s；强制美国区数据 |
| **本地数据导入** | 用户上传 JSON/CSV 格式评论文件 | 标准化后的评论列表 | 支持文档化的 JSON/CSV 格式；自动识别 RSS 原始结构和已标准化结构；10MB 内文件解析无卡顿 |
| **评论清洗与去重** | 原始评论列表 | 清洗后评论 + 清洗报告 | 按 review_id 去重；无 ID 时按内容 MD5 去重；字段标准化（rating→int 1-5、version→字符串、date→ISO格式）；语言检测标记；空内容/纯emoji标记为 low_quality 但不删除；输出清洗报告（去重数、过滤数、语言分布） |
| **分析范围确定** | 用户输入自然语言分析目标（如"focus on subscription conversion and low ratings for version 2.0+"） | 结构化过滤配置 + 范围说明 | LLM 解析自然语言为过滤条件（版本、星级、主题提示、时间范围）；规则执行过滤；过滤后<20条时警告"样本量不足"；数据充分性初判 |
| **AI 动态主题发现** | 清洗后评论 + 分析目标 | 动态主题列表（主题名、描述、关联评论ID、样本数、情感分布、置信度、冲突证据） | LLM 动态归纳 5-10 个主题，**不使用预设分类**；主题命名来自评论中的具体问题；每批30条评论批量处理；输出严格 JSON；review_id 必须来自真实输入，编造的 ID 被代码过滤 |
| **单条评论语义标注** | 清洗后评论 | 每条评论的主题归属、情感、备注 | 每条评论归入动态发现的主题；情感标签 positive/negative/neutral；无效 ID 被过滤 |
| **证据充分性评估** | 主题列表 + 评论数据 | 每个主题的置信度、矛盾反馈、不确定性说明 | 置信度 high/medium/low；存在对立观点时记录 conflicting_evidence；样本量不足时自动降级为 low；模型生成结论与确定性统计可区分 |
| **PRD 与需求生成** | 分析结果（主题+证据）+ 分析目标 | PRD 文档（问题概述、需求列表、版本规划） | 每个需求带 req_id、标题、描述、优先级 P0-P3、来源主题、source_review_ids、验收标准、置信度；需求描述基于评论证据，不编造 |
| **多版本规划** | 需求列表 | 版本计划（多版本拆分，每版含目标、范围、需求ID、拆分理由） | 按优先级+工作量+依赖关系拆分为多个版本；每版有明确目标和范围；至少拆分 2 个版本 |
| **测试用例生成** | PRD 需求 + 评论数据 | 测试用例套件 | 每条用例带 case_id、req_id、标题、前置条件、步骤、预期结果、source_review_ids、类型、置信度；用例能验证需求是否解决了评论中的问题；无效 req_id/review_id 被过滤 |
| **可追溯性验证** | PRD + 测试用例 + 评论数据 | 验证报告（通过率、未通过项、假设结论列表） | 校验每个需求的 source_review_ids 存在性；校验每个用例的 req_id 有效性和 review_ids 存在性；无证据的需求标记为 assumption；输出通过率和明细；纯规则校验，确定性可复现 |
| **语义一致性校验（可选）** | PRD 需求 + 对应评论原文 | 语义校验结果（通过/不通过+原因） | LLM 抽查需求描述是否真的能从评论中推导；不通过的标记为 assumption；LLM 不可用时跳过并记录，不影响整体验证 |
| **Streamlit Web UI** | 用户交互 | 可运行的 Web 界面 | 输入区（App链接+分析目标+数据来源选择）；执行进度展示（st.status 步骤指示器+中间结果）；结果分区（原始评论/清洗报告/分析结果/PRD/测试用例/验证报告）；无 API Key 时自动加载缓存示例数据并醒目标记 |
| **离线缓存支持** | 无网络/无 API Key 环境 | 预生成的完整分析结果缓存 | 至少1份笔试指定 App（839285684）的完整管线输出缓存；UI 自动检测 LLM 配置缺失并加载缓存；缓存数据明确标记"非实时分析结果"；不替代实时处理能力 |

## 三、非功能性需求（系统底线）

### 3.1 性能与响应

| 指标 | 要求 |
|:---|:---|
| 评论抓取 | 每页请求间隔≥1.5s，最多10页，总耗时≤30s |
| LLM 批量分析 | 每批30条评论，单批响应≤30s；500条评论总分批≤17批 |
| UI 交互 | 侧栏/筛选切换后图表刷新≤2s；步骤进度实时更新无卡顿 |
| 文件导入 | 10MB 内 JSON/CSV 解析≤5s |

### 3.2 安全与合规

| 约束 | 要求 |
|:---|:---|
| 密钥管理 | API Key 通过环境变量（`.env`）配置，绝不硬编码；`.env` 在 `.gitignore` 中排除 |
| 数据来源 | 使用 Apple 官方 RSS Feed，不爬取页面可见内容，遵守目标站点速率限制 |
| 敏感信息 | 评论中的用户信息仅展示作者名，不存储或展示其他个人数据 |
| 内容安全 | LLM 输出经过 JSON 解析和 ID 校验，防止注入或编造数据 |

### 3.3 可扩展性与可维护性

| 约束 | 要求 |
|:---|:---|
| 模块化架构 | 抓取/清洗/分析/PRD/测试用例/验证各模块独立，通过 orchestrator 编排 |
| LLM 可替换 | 通过统一 LLMClient 封装，支持 DeepSeek/OpenAI 等兼容 API，切换仅改配置 |
| 配置外部化 | 所有可调参数（模型、温度、页数、间隔）通过 config.py 和环境变量管理 |
| 代码规范 | Python 类型注解、docstring、模块头部职责说明 |

### 3.4 可靠性与容错

| 约束 | 要求 |
|:---|:---|
| LLM 调用失败 | 指数退避重试3次（1s/2s/4s）；重试耗尽后抛出明确异常，不静默 |
| JSON 解析容错 | LLM 输出非严格 JSON 时，使用 safe_json_loads 容错解析；解析失败记录日志 |
| 步骤级容错 | 某步骤失败不影响已完成步骤的结果展示，orchestrator 记录失败状态和错误信息 |
| 缓存降级 | 无 API Key 时自动加载离线缓存，保证 UI 可演示 |

## 四、接入边界与风险控制

### 4.1 当前版本边界

- **数据范围**：仅支持美国区 App Store 评论（Apple RSS 限制最多约500条），不支持其他应用商店
- **分析语言**：主要针对英文评论，支持多语言检测但不做翻译
- **输出形式**：纯文本交互 + 结构化 JSON，不直接对接 Jira/飞书等项目管理工具
- **模型能力**：依赖外部 LLM API，不内置本地模型

### 4.2 风险识别与对策

| 风险 | 影响 | 对策 |
|:---|:---|:---|
| Apple RSS 数据量有限（最多500条） | 评论覆盖不全，可能遗漏长尾问题 | UI 透明说明数据限制；分析结果中标注样本量和置信度 |
| LLM 编造 review_id | 可追溯链断裂，结论无依据 | 三重防护：Prompt 约束 + 生成时代码过滤无效 ID + validator 再校验 |
| LLM 调用成本高/限流 | 大量评论分析耗时久或失败 | 批量处理（30条/批）+ 指数退避重试 + 失败时明确提示 |
| 无 API Key 环境无法演示 | 面试官看不到完整效果 | 预生成离线缓存 + UI 自动加载 + 醒目标记 |
| 不同 App 输出质量差异 | 泛化能力不足 | 动态主题发现不预设分类，Prompt 通用化设计；支持导入任意评论数据 |

### 4.3 验收口径汇总

1. **功能完整性**：上述15个功能模块全部实现，端到端流程可跑通
2. **数据真实性**：评论来自 Apple RSS Feed，可复现，来源和限制透明说明
3. **动态分析**：LLM 动态发现主题，无固定分类映射；换不同 App 输出不同主题
4. **可追溯性**：每个需求和测试用例都带 source_review_ids，validator 校验通过率100%
5. **证据驱动**：每个发现带样本数、置信度、冲突证据；无依据结论标记为 assumption
6. **UI 可用性**：Streamlit 可本地运行，进度实时展示，结果分区清晰
7. **离线可演示**：无 API Key 时自动加载缓存，标记明确
8. **代码质量**：模块化、类型注解、配置外部化、密钥安全
