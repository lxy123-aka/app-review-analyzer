# S1 需求拆解清单

> 项目：App Store 评论分析与版本规划工具
> 阶段：需求拆解
> 日期：2026-08-20

---

## 一、项目目标与业务价值

### 1.1 项目背景

产品团队在迭代 App 时，需要从海量用户评论中挖掘真实痛点、规划版本需求、设计测试用例。传统方式依赖人工逐条阅读评论，效率低、易遗漏、难以量化。本项目旨在构建一个**基于大模型的 App Store 评论全流程分析工具**，将"评论→问题→需求→测试用例"的链路自动化、可追溯化。

### 1.2 核心目标

- **数据真实可复现**：通过 Apple 官方 RSS Feed 抓取美国区真实评论数据，不依赖页面爬取
- **动态语义分析**：由 LLM 从评论中自动发现问题主题，不使用固定关键词映射或预定义分类
- **全链路可追溯**：每条需求、每个测试用例都能回溯到具体的用户评论 ID
- **证据驱动**：每个发现都附带源评论、样本数、置信度和冲突证据，杜绝无依据结论
- **可本地运行**：Streamlit Web UI，单条命令启动，支持离线缓存演示

### 1.3 业务价值

| 价值维度 | 描述 |
|:---|:---|
| **效率提升** | 将人工阅读数百条评论并归纳问题的时间从数小时缩短至分钟级 |
| **决策质量** | 基于真实评论证据生成 PRD，减少主观臆断和"拍脑袋"需求 |
| **测试覆盖** | 自动生成与需求、评论关联的测试用例，确保用户痛点被验证 |
| **团队协作** | 结构化输出便于产品、研发、测试团队对齐需求来源和优先级 |

## 二、核心功能需求矩阵

> 验收标准说明：每条均为可量化、可测试、可验证的具体指标，标注【可验证】表示可通过代码审查/运行测试/数据检查直接验证。

| 编号 | 功能模块 | 核心输入/触发条件 | 预期输出 | 验收标准（可量化/可执行/可验证） |
|:---|:---|:---|:---|:---|
| F01 | **App Store 评论抓取** | 用户输入美国区 App Store 链接（如 `https://apps.apple.com/us/app/xxx/id839285684`） | 结构化评论列表（review_id、内容、评分、版本、作者、日期）+ CollectReport | 【可验证】①数据源为 Apple 官方 RSS Feed（`itunes.apple.com/{country}/rss/customerreviews/...`），非页面 HTML 爬取，可通过 collector.py 源码验证；②支持分页循环，最多 10 页/约 500 条，空页自动提前终止；③每页请求间隔 ≥1.5s，可通过 config.py REQUEST_INTERVAL 验证；④强制美国区数据（country=us），即使输入 cn 链接也切换为 us；⑤抓取失败时指数退避重试 3 次（1s/2s/4s），不静默崩溃；⑥输出 CollectReport 含 pages_attempted/pages_succeeded/raw_count/data_source 字段 |
| F02 | **本地数据导入** | 用户上传 JSON/CSV 格式评论文件（≤10MB） | 标准化后的评论列表 + CollectReport | 【可验证】①支持 2 种 JSON 格式（已标准化列表 / RSS 原始 `{"feed":{"entry":[...]}}` 结构）+ 1 种 CSV 格式，格式文档见 DATA_SOURCE.md；②自动识别格式，无需用户指定；③10MB 内文件解析耗时 ≤5s；④导入失败时给出明确错误提示（格式错误/编码错误/字段缺失），不崩溃；⑤导入数据进入后续清洗流程，与抓取数据处理一致 |
| F03 | **评论清洗与去重** | 原始评论列表（F01/F02 输出） | 清洗后评论列表 + CleanReport | 【可验证】①按 review_id 去重，重复评论去重率 100%；②无 review_id 时按 content MD5 哈希去重；③字段标准化：rating 转为 int 1-5（非法值标记 None 并记录 cleaning_notes），version 统一字符串去空格，date 转 ISO 8601 格式；④语言检测（langdetect），标记 language 字段；⑤空内容（长度<5）/纯 emoji 标记为 low_quality 但不删除；⑥输出 CleanReport 含 raw_count/clean_count/duplicate_count/low_quality_count/language_distribution 字段；⑦清洗后评论 review_id 唯一率 100% |
| F04 | **分析范围确定** | 用户输入自然语言分析目标（如"focus on subscription conversion and low ratings for version 2.0+"） | 结构化过滤配置（version_filter/rating_filter/topic_hint/time_range）+ 范围说明 | 【可验证】①LLM 将自然语言解析为结构化过滤配置（JSON 格式），支持版本/星级/主题提示/时间范围 4 类过滤条件；②规则引擎执行过滤（pandas query），过滤结果可复现；③过滤后评论数 <20 条时，UI 显示警告"样本量不足，结论置信度降低"；④数据充分性初判：≥100 条→high，50-99 条→medium，<50 条→low；⑤分析目标为空时不过滤，使用全量数据 |
| F05 | **AI 动态主题发现** | 清洗后评论（F03 输出）+ 分析目标（F04 输出） | 动态主题列表（topic/description/review_ids/sample_count/sentiment/confidence/conflicting_evidence）+ per_review 标注 | 【可验证】①LLM 动态归纳 5-10 个主题，**代码中无预设分类列表/关键词映射表**，可通过 analyzer.py SYSTEM_PROMPT 源码验证；②主题命名来自评论中的具体问题（如"订阅自动续费缺乏提醒"），非笼统分类（如"价格问题"）；③每批 30 条评论批量调用 LLM，500 条分 ≤17 批；④输出严格 JSON，safe_json_loads 容错解析；⑤review_id 过滤：LLM 输出的 review_ids 经 valid_ids 集合校验，编造 ID 过滤率 100%；⑥sample_count 由代码重算为 len(filtered review_ids)，不信任 LLM 输出值；⑦跨批次同名主题合并，review_ids 取并集，置信度降级规则（任一批 low→整体 low）；⑧换不同 App 输入，输出主题名称和数量不同，证明无硬编码 |
| F06 | **单条评论语义标注** | 清洗后评论（F03 输出） | 每条评论的 primary_topic/sentiment/note 标注 | 【可验证】①每条评论归入 F05 动态发现的主题之一（primary_topic 字段）；②情感标签 positive/negative/neutral 三分类；③标注覆盖率 ≥95%（未标注的评论记录 note="未归类"）；④无效 review_id 标注被过滤，不进入结果；⑤标注结果与主题 review_ids 一致（某主题的 review_ids 中的评论，其 primary_topic 等于该主题名） |
| F07 | **证据充分性评估** | 主题列表（F05 输出）+ 评论数据（F03 输出） | 每个主题的 confidence/conflicting_evidence/uncertainty 评估 | 【可验证】①置信度 high/medium/low 三级，判定规则：sample_count≥10 且观点一致→high，5-9 条→medium，<5 条→low；②存在对立观点（同一主题内既有正面又有负面评论）时，conflicting_evidence 字段记录矛盾描述和对立评论 ID；③样本量不足时 confidence 自动降级为 low；④模型生成结论（主题描述/矛盾反馈）与确定性统计（sample_count/情感分布）在 UI 上用不同标签区分（🤖模型生成 / 📊确定性统计）；⑤每个主题的 evidence_type 字段标记来源 |
| F08 | **PRD 与需求生成** | 分析结果（F05/F07 输出）+ 分析目标（F04 输出） | PRD 文档（problem_summary + requirements[] + version_plan[]） | 【可验证】①每个需求含 8 个字段：req_id/title/description/priority(P0-P3)/source_topic/source_review_ids/acceptance_criteria/confidence；②100% 需求带非空 source_review_ids，可通过 validator 验证；③需求描述基于评论证据概括，不编造评论中不存在的功能；④优先级 P0-P3 四级，P0 需求数 ≤ 总需求 30%；⑤每个需求的 acceptance_criteria 为可验证的具体描述，非空泛表述；⑥problem_summary 基于主题分析结果概括，不引入无证据的问题 |
| F09 | **多版本规划** | 需求列表（F08 输出） | version_plan[]（每版含 version/goal/scope/req_ids/rationale） | 【可验证】①至少拆分为 2 个版本，可通过 prd_generator.py 输出验证；②每版含 version/goal/scope/req_ids/rationale 5 个字段；③版本拆分依据：优先级（P0 优先入 v1）+ 依赖关系 + 工作量估算；④每版需求数 ≤ 总需求数 60%，避免单版过载；⑤每版 goal 明确可衡量，scope 描述清晰不重叠；⑥rationale 字段说明拆分理由，非空 |
| F10 | **测试用例生成** | PRD 需求（F08 输出）+ 评论数据（F03 输出） | test_suite（test_cases[] + notes） | 【可验证】①每条用例含 9 个字段：case_id/req_id/title/preconditions/steps[]/expected_result/source_review_ids/type/confidence；②100% 用例带有效 req_id（存在于需求列表），无效 req_id 用例过滤率 100%；③100% 用例带非空 source_review_ids，且 ID 存在于原始评论数据；④steps 为非空列表（≥1 步），expected_result 为可验证的具体描述；⑤用例类型 functional/regression/edge_case 三类；⑥用例预期结果能验证对应需求是否解决了 source_review_ids 评论中提出的问题；⑦每个需求至少有 1 条测试用例覆盖，覆盖率 100% |
| F11 | **可追溯性验证** | PRD（F08）+ test_suite（F10）+ 评论数据（F03） | ValidationReport（total/passed/failed/pass_rate/items[]/assumed_conclusions[]） | 【可验证】①校验范围：100% 需求的 source_review_ids 存在性 + 100% 用例的 req_id 有效性 + 100% 用例的 source_review_ids 存在性；②无证据需求（source_review_ids 为空或全无效）100% 标记为 assumption，进入 assumed_conclusions 列表；③部分 ID 无效的需求/用例，记录无效数量和有效数量，通过但保留明细；④输出 pass_rate 百分比，精确到小数点后 2 位；⑤items[] 列表含 target/target_type/passed/reason/related_ids 5 字段，可追溯每条校验结果；⑥纯规则校验（无 LLM），同一输入多次运行结果 100% 一致（确定性可复现）；⑦校验耗时 <1s（纯集合查找和循环） |
| F12 | **语义一致性校验（可选增强）** | PRD 需求（F08）+ 对应评论原文（F03） | 语义校验结果列表（req_id/passed/reason/confidence） | 【可验证】①随机抽取 ≥20% 的需求做语义校验（sample_size 可配置，默认 3 条或 20% 取大）；②LLM 判断需求描述是否真的能从其 source_review_ids 对应的评论原文中推导出来；③输出严格 JSON：{"passed":true/false,"reason":"...","confidence":"high/medium/low"}；④不通过的需求 100% 标记为 assumption，加入 assumed_conclusions 列表；⑤LLM 不可用时（API Key 缺失/调用失败）自动跳过，记录 notes="语义一致性校验跳过（LLM 不可用）"，不影响 F11 主验证流程；⑥校验结果在 UI 上用红色单独列出，标注"🤖语义校验未通过" |
| F13 | **Streamlit Web UI** | 用户交互操作 | 可运行的 Web 界面（`streamlit run app.py` 启动） | 【可验证】①输入区含 3 个控件：App Store 链接输入框 + 分析目标自由文本框 + 数据来源选择（在线抓取/上传文件/加载样本/加载缓存）；②执行进度展示：st.status 步骤指示器实时更新 8 个步骤（load_cache/collect/clean/analyze/prd/testcase/validate/done），每步完成后显示中间结果摘要；③结果分区含 6 个 expander：原始评论/清洗报告/AI分析结果/PRD/测试用例/验证报告；④无 API Key 时自动加载缓存（F14），顶部 st.warning 醒目标记；⑤UI 切换 Tab/expander 不重新执行流水线（session_state 持久化）；⑥`streamlit run app.py` 命令可直接启动，浏览器自动打开 localhost:8501 |
| F14 | **离线缓存支持** | 无网络/无 API Key 环境 | 预生成的完整分析结果缓存（JSON） | 【可验证】①至少 1 份笔试指定 App（ID: 839285684）的完整管线输出缓存，文件路径 data/cached_result_app_839285684.json，含 reviews_raw/reviews_clean/analysis/prd/test_suite/validation 全部分区数据；②UI 启动时自动检测 LLM 配置（settings.validate_llm()），缺失且无结果时自动加载缓存；③缓存模式下结果区顶部显示 st.warning："⚠️ 当前显示缓存示例数据（App ID: 839285684），非实时分析结果"，标记可见；④提供手动"加载离线缓存结果"按钮作为兜底；⑤缓存数据不替代实时处理能力：配置 API Key 后可正常输入任意 App 链接实时分析；⑥缓存文件生成脚本 generate_cache_839.py 可复现，非手工编造 |

## 三、非功能性需求（系统底线）

### 3.1 性能与响应

| 指标 | 要求 |
|:---|:---|
| 评论抓取 | 每页请求间隔≥1.5s，最多10页，总耗时≤30s |
| LLM 批量分析 | 每批30条评论，单批响应≤30s；500条评论总分批≤17批 |
| UI 交互 | 侧栏/筛选切换后图表刷新≤2s；步骤进度实时更新无卡顿 |
| 文件导入 | 10MB 内 JSON/CSV 解析≤5s |

### 3.2 安全与合规

| 约束 | 要求 |
|:---|:---|
| 密钥管理 | API Key 通过环境变量（`.env`）配置，绝不硬编码；`.env` 在 `.gitignore` 中排除 |
| 数据来源 | 使用 Apple 官方 RSS Feed，不爬取页面可见内容，遵守目标站点速率限制 |
| 敏感信息 | 评论中的用户信息仅展示作者名，不存储或展示其他个人数据 |
| 内容安全 | LLM 输出经过 JSON 解析和 ID 校验，防止注入或编造数据 |

### 3.3 可扩展性与可维护性

| 约束 | 要求 |
|:---|:---|
| 模块化架构 | 抓取/清洗/分析/PRD/测试用例/验证各模块独立，通过 orchestrator 编排 |
| LLM 可替换 | 通过统一 LLMClient 封装，支持 DeepSeek/OpenAI 等兼容 API，切换仅改配置 |
| 配置外部化 | 所有可调参数（模型、温度、页数、间隔）通过 config.py 和环境变量管理 |
| 代码规范 | Python 类型注解、docstring、模块头部职责说明 |

### 3.4 可靠性与容错

| 约束 | 要求 |
|:---|:---|
| LLM 调用失败 | 指数退避重试3次（1s/2s/4s）；重试耗尽后抛出明确异常，不静默 |
| JSON 解析容错 | LLM 输出非严格 JSON 时，使用 safe_json_loads 容错解析；解析失败记录日志 |
| 步骤级容错 | 某步骤失败不影响已完成步骤的结果展示，orchestrator 记录失败状态和错误信息 |
| 缓存降级 | 无 API Key 时自动加载离线缓存，保证 UI 可演示 |

## 四、接入边界与风险控制

### 4.1 当前版本边界

- **数据范围**：仅支持美国区 App Store 评论（Apple RSS 限制最多约500条），不支持其他应用商店
- **分析语言**：主要针对英文评论，支持多语言检测但不做翻译
- **输出形式**：纯文本交互 + 结构化 JSON，不直接对接 Jira/飞书等项目管理工具
- **模型能力**：依赖外部 LLM API，不内置本地模型

### 4.2 风险识别与对策

| 风险 | 影响 | 对策 |
|:---|:---|:---|
| Apple RSS 数据量有限（最多500条） | 评论覆盖不全，可能遗漏长尾问题 | UI 透明说明数据限制；分析结果中标注样本量和置信度 |
| LLM 编造 review_id | 可追溯链断裂，结论无依据 | 三重防护：Prompt 约束 + 生成时代码过滤无效 ID + validator 再校验 |
| LLM 调用成本高/限流 | 大量评论分析耗时久或失败 | 批量处理（30条/批）+ 指数退避重试 + 失败时明确提示 |
| 无 API Key 环境无法演示 | 面试官看不到完整效果 | 预生成离线缓存 + UI 自动加载 + 醒目标记 |
| 不同 App 输出质量差异 | 泛化能力不足 | 动态主题发现不预设分类，Prompt 通用化设计；支持导入任意评论数据 |

### 4.3 验收口径汇总

1. **功能完整性**：上述15个功能模块全部实现，端到端流程可跑通
2. **数据真实性**：评论来自 Apple RSS Feed，可复现，来源和限制透明说明
3. **动态分析**：LLM 动态发现主题，无固定分类映射；换不同 App 输出不同主题
4. **可追溯性**：每个需求和测试用例都带 source_review_ids，validator 校验通过率100%
5. **证据驱动**：每个发现带样本数、置信度、冲突证据；无依据结论标记为 assumption
6. **UI 可用性**：Streamlit 可本地运行，进度实时展示，结果分区清晰
7. **离线可演示**：无 API Key 时自动加载缓存，标记明确
8. **代码质量**：模块化、类型注解、配置外部化、密钥安全

## 五、功能模块优先级排序

基于业务价值、技术依赖关系和笔试硬性要求，对 15 项核心功能按 P0/P1/P2 三级排序：

| 优先级 | 功能模块 | 排序理由 |
|:---|:---|:---|
| **P0** | App Store 评论抓取 | 数据源头，所有后续模块的输入依赖，笔试要求"真实数据抓取" |
| **P0** | 评论清洗与去重 | 数据质量保障，去重和标准化是分析准确性的前提 |
| **P0** | AI 动态主题发现 | 核心语义模块，笔试硬性要求"至少一个核心语义任务模型驱动"，项目差异化核心 |
| **P0** | 证据充分性评估 | 笔试硬性要求"evaluate whether the available evidence is sufficient, identify conflicting feedback" |
| **P0** | 可追溯性验证 | 笔试硬性要求"validate the traceability chain"，质量保障核心 |
| **P1** | PRD 与需求生成 | 产品价值输出，笔试要求"create an update plan, produce a PRD" |
| **P1** | 多版本规划 | 笔试要求"split the scope into multiple versions when necessary" |
| **P1** | 测试用例生成 | 笔试要求"generate test cases based on the PRD, each linked to its requirement and source reviews" |
| **P1** | 分析范围确定 | 支持用户输入分析目标/约束，笔试要求"user should also be able to provide an analysis goal or constraint" |
| **P1** | Streamlit Web UI | 笔试要求"final results should be presented through a runnable UI"，交互展示层 |
| **P1** | 执行进度展示 | 笔试要求"display the execution progress in the UI, including stages, intermediate results, validation results, errors, and revisions" |
| **P2** | 本地数据导入（JSON/CSV） | 笔试要求"support importing review data from a documented JSON or CSV format"，扩展功能非主流程 |
| **P2** | 离线缓存支持 | 体验优化，保障无 API Key 环境可演示，非核心链路 |
| **P2** | 语义一致性校验（可选） | 增强型验证，LLM 不可用时可跳过，非笔试硬性要求 |
| **P2** | 模型/统计结论 UI 区分 | 体验优化，笔试要求"model-generated conclusions must remain distinguishable from deterministic statistics" |

**实施路径**：P0 模块先独立开发并单元测试 → P1 模块基于 P0 输出开发并集成 → P2 模块在全链路跑通后优化补充。

## 六、需求矛盾点与资源权衡分析

### 矛盾点 1：分析全面性 vs 数据量限制（Apple RSS 最多 500 条）

| 维度 | 追求全面性 | 接受数据量限制 |
|:---|:---|:---|
| 需求目标 | 覆盖尽可能多的历史评论，减少长尾问题遗漏 | 使用官方稳定接口，合规可复现 |
| 资源消耗 | 需要爬取页面或多数据源，开发成本高，有反爬风险 | 实现简单，Apple RSS 官方接口稳定 |
| 风险 | 违反笔试"不应只爬取页面可见内容"要求，可能被目标站点限流 | 最多 500 条，早期版本评论可能遗漏，分析样本有限 |

**权衡决策**：**接受 500 条限制，透明告知 + 多维度弥补**——
- 使用 Apple 官方 RSS Feed，符合笔试"探索更合适的数据获取方式"的要求，合规稳定
- 在 UI 和文档中**透明说明数据限制**，不隐瞒不夸大
- 分析结果中每条发现都标注样本数和置信度，数据不足时自动降级 confidence=low
- 支持导入外部 JSON/CSV 补充数据，给用户留扩展口
- 笔试指定 App（839285684）预生成完整缓存，确保面试官可审查

### 矛盾点 2：LLM 动态分析灵活性 vs 结果确定性与可追溯性

| 维度 | LLM 全流程驱动 | 规则确定性为主 |
|:---|:---|:---|
| 需求目标 | 动态发现任意 App 的问题主题，泛化能力强 | 结果可复现，无幻觉，可追溯链完整 |
| 资源消耗 | LLM 调用成本高（500条评论约10+次调用），有随机性 | 执行快，成本低，结果确定 |
| 风险 | LLM 可能编造 review_id，结论无依据，可追溯链断裂 | 无法处理未预设分类，泛化能力差，不满足笔试"动态分类"硬性要求 |

**权衡决策**：**混合策略，LLM 做语义 + 规则做校验**——
- 主题发现、需求生成、测试用例生成等**语义理解任务**用 LLM（满足笔试"模型驱动"硬性要求，保证泛化能力）
- 去重、字段标准化、ID 存在性校验等**确定性操作**用规则（保证可复现、低成本、无幻觉）
- LLM 输出后用规则做**三重后处理校验**（Prompt 约束禁止编造 ID → 生成时 valid_ids 集合过滤 → validator 再校验），兼顾灵活性和可追溯性
- 过滤后样本不足的发现标记 confidence=low，不丢弃但明确告知不确定性

### 矛盾点 3：功能全面性 vs 项目周期与开发资源

| 维度 | 功能全覆盖 | 聚焦核心功能 |
|:---|:---|:---|
| 需求目标 | 覆盖笔试所有 23 项验收标准，功能丰富展示全面能力 | 核心功能质量高，稳定可靠，周期内可完成 |
| 资源消耗 | 开发周期长，联调测试时间不足，部分功能可能粗糙 | 可能遗漏笔试部分要求，功能展示不够全面 |
| 风险 | 联调不充分，交付时可能有 bug，影响面试官体验 | 笔试硬性要求遗漏，直接扣分 |

**权衡决策**：**笔试硬性要求全覆盖 + 核心功能深度打磨 + 边缘功能合理降级**——
- 笔试 23 项验收标准**全部覆盖**，不遗漏任何硬性要求（这是底线）
- 核心功能（动态主题发现、防幻觉三重防护、可追溯验证、PRD+测试用例生成）**深度打磨**，联调充分，自测全覆盖
- 边缘功能（语义一致性校验、多版本规划细节、模型/统计 UI 区分）作为**可选增强**，LLM 不可用时优雅降级，不阻塞主流程
- 离线缓存作为**兜底方案**，确保无 API Key 环境也能展示完整效果，不依赖实时运行
- 采用 vibe coding 模式提升开发效率，AI 辅助生成代码+人工核心架构把控+全面代码审查

### 矛盾点 4：UI 展示丰富度 vs 开发复杂度与运行稳定性

| 维度 | 丰富交互式 UI | 简洁稳定 UI |
|:---|:---|:---|
| 需求目标 | 面试官可查看所有中间结果和交付物，体现全流程 | 界面清爽，运行稳定，不崩溃 |
| 资源消耗 | Streamlit 复杂状态管理难，容易出现重渲染重复计算，调试成本高 | 功能简单，可能展示不足，面试官看不到完整分析过程 |
| 风险 | UI bug 导致应用崩溃，面试官体验差 | 笔试要求"display execution progress including stages, intermediate results, validation results, errors, and revisions"可能不满足 |

**权衡决策**：**分区展示 + 可折叠 + 状态持久化**——
- 6 个结果分区（原始评论/清洗报告/分析结果/PRD/测试用例/验证报告）用 expander 组织，关键结果默认展开
- 执行进度用 `st.status` 实时展示，每步完成后显示中间结果摘要
- 用 `st.session_state` 持久化流水线结果，按钮触发才重新执行，解决 Streamlit 重渲染重复计算问题
- 缓存模式下顶部 `st.warning` 醒目标记，不干扰正常结果展示
- 不追求复杂动画和交互，优先保证运行稳定和信息完整
